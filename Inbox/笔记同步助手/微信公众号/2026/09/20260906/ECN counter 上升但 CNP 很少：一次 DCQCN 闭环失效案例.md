<u>00</u>

奇了怪了

交换机上看，ECN counter 确实在涨。  
说明队列确实拥塞过。  
说明交换机也确实在打标。

可服务器上再一看。  
CNP 很少。  
发送端速率也没明显收敛。  
训练任务还是抖。  
NCCL Collective latency 还是长尾。  
慢 Rank 还是时不时冒出来。

这时候，会下意识认为：

“交换机都打 ECN 了，DCQCN 不就应该工作了吗？”

不一定。

**ECN counter 上升，只能证明‘拥塞被看见了’。**  
**CNP 能不能回得来、发送端会不会降速，才决定 DCQCN 闭环有没有真正跑起来。**

  

> 在 RoCE 网络里，ECN 打标只是开始，不是结束；真正决定拥塞是否被控制住的，是后面的 CNP 和速率回调有没有形成闭环。

  

<u>01</u>

训练没挂，但越来越慢

这次故障发生在一个 RoCE 训练集群里。

现象不是“直接崩”。  
而是“慢慢变坏”。

训练任务能跑。  
链路也都 Up。  
NCCL 没有明显报错。  
但 Step Time 开始抖。  
GPU Util 开始掉。  
AllReduce 的尾延迟越来越难看。

再往下看交换机。

承载无损流量的那个 lossless 队列，ECN counter 持续上涨。  
说明交换机队列水位确实碰到了 ECN 阈值。  
也说明流量不是“完全正常”。

可问题来了。

接收端网卡侧看到的 CNP 很少。  
发送端也没有出现预期中的明显降速。  
拥塞没有被及时“压回来”。  
队列高水位持续存在。  
偶尔还伴随着 PFC Pause。

这就是这次故障最关键的反常点：

**交换机已经在喊堵了。**  
**但发送端像没怎么听见。**

  

> 训练现场最危险的状态，不是“交换机拥塞过”，而是“交换机已经拥塞了，但发送端没有有效收敛”。

<u>02</u>

DCQCN 闭环到底是怎么工作的

在 RoCE 场景里，交换机发现队列水位高了。  
如果配置了 ECN，它会对经过的 RoCE 数据包做 CE 标记。

这些被标记过的数据包到了接收端。  
接收端网卡识别出拥塞标记后，会按机制生成 CNP。  
这个 CNP 再回给发送端。

发送端网卡收到 CNP 后，DCQCN 才会开始起作用。  
也就是调低发送速率。  
让后续流量别再一股脑冲上去。

如果这个闭环是通的，正常表现一般是：

-   队列上升
    
-   ECN 打标出现
    
-   CNP 回来
    
-   发送端收敛
    
-   队列逐步回落
    

这才叫闭环。

所以一定要记住：

交换机不负责帮你“自动降速”。

交换机只负责“提醒你堵了”。

真正降速的是发送端。  
而发送端要降速，前提是它收到了有效的拥塞反馈。  
这个反馈，在 DCQCN 里通常就是 CNP。

  

> ECN 是交换机发出的“拥塞信号”，CNP 是接收端回给发送端的“反馈包”，DCQCN 则是发送端真正执行降速的机制。

<u>03</u>

为什么“ECN 多，CNP 少”不一定 1:1，但也绝不能视而不见

这里要特别强调一个误区：

**ECN counter 和 CNP counter，本来就不应该简单追求 1:1。**

为什么？

因为它们不在同一个观察面。

交换机上的 ECN counter，通常是端口、队列、时间窗口维度的累计计数。  
而服务器上的 CNP counter，通常是某个主机、某个端口、某类流量的计数。

再加上不同网卡、驱动、固件版本下，CNP 的生成和统计口径可能也不完全一样。  
有些实现还会做一定的抑制或节流。

所以不能机械地认为：

交换机打了 1000 次 ECN，主机就一定要看到 1000 个 CNP。

但是，如果看到的是这种情况：

-   ECN counter 长时间明显上涨；
    
-   队列高水位持续出现；
    
-   训练性能确实在抖；
    
-   而 CNP 很少；
    
-   发送端速率也不明显变化；
    

那这就不是“计数器不相等”这么简单了。

这时候更应该怀疑：

**拥塞反馈并没有有效闭环**

  

> ECN 和 CNP 不要求数值一一对应，但如果前者持续明显上升、后者却长期偏少，同时发送端也不收敛，那就要怀疑闭环失效。

![[Inbox/笔记同步助手/微信公众号/2026/09/images/3f4288b8785c2e197759f37d96470300_MD5.jpg]]

<u>04</u>

这次故障，是怎么一步步垮掉的

这次任务是典型的训练流量模型。

不是推理。  
不是 KV Cache 迁移。  
不是 Prefill / Decode 的请求尾延迟问题。

而是训练里的同步通信。

主要表现为 AllReduce / ReduceScatter 这类 Collective 流量。  
业务高峰阶段，多个节点同时把流量打向同一个方向。  
局部 Incast 非常明显。

结果就是：

某些 Leaf 端口的 lossless 队列先抬头。  
随后 ECN 开始打标。  
但由于拥塞反馈没有有效回到发送端，发送端没有及时降速。

于是同一批流量继续冲。  
队列继续高。  
PFC 开始零星出现。  
NCCL 某些 Rank 的 collective latency 开始拉长。  
慢 Rank 被放大。  
最后整轮训练 Step 都被拖慢。

这里非常关键的一点是：

**这不是“没有拥塞”**

恰恰相反。  
这是“拥塞已经被交换机看到，但没有被端到端机制及时控制住”。

换句话说，交换机看见了火。  
但灭火器没喷出来。

  

> DCQCN 最怕的不是拥塞，而是“拥塞已经发生，但反馈链条没有及时让发送端收敛”。

![[Inbox/笔记同步助手/微信公众号/2026/09/images/0af97183a9c8dc6f559a70af189545c8_MD5.jpg]]

<u>05</u>

根因不是交换机没打标，而是接收侧反馈链条没形成有效闭环

最后复盘下来，问题并不在交换机“有没有打 ECN”。

交换机是在打标的。  
这一点从 ECN counter 就能看出来。

真正的问题在接收侧和端侧闭环。

这次案例里，部分节点的 RoCE/DCQCN 相关配置没有和集群统一。  
更准确地说：

**接收侧对拥塞标记的处理和反馈，没有按预期形成有效的 CNP 回送。**

至于具体为什么没形成，在不同驱动、OFED 版本、固件版本、参数路径下，表现可能不完全一样：

-   有的可能是版本不一致
    
-   有的可能是参数没有真正生效
    
-   有的可能是配置漂移
    
-   有的可能是只改了发送侧，没改接收侧
    

  

这里没有用某一个特别死的参数名来写死。  
因为不同现场不一样。

但逻辑是确定的：

-   交换机已经在给 CE
    
-   接收端却没有按预期把拥塞反馈有效送回去
    
-   于是发送端拿不到足够的反馈信号
    
-   DCQCN 也就谈不上有效调速
    

  

所以，这次故障的本质不是“ECN 不工作”。

而是：

**ECN 在工作，但 DCQCN 闭环没有完整工作。**

  

> 交换机能打标，不等于发送端一定会降速；中间还隔着接收端的反馈和发送端的执行。

![[Inbox/笔记同步助手/微信公众号/2026/09/images/7e394352c1055a1f31119d73a1219d21_MD5.jpg]]

<u>06</u>

为什么这种问题会把 NCCL 和训练性能拖得很难看

到了这里，就能把训练性能和网络现象串起来了。

训练里很多通信不是“谁慢谁自己承担”。

而是 Collective。

AllReduce 里，一个 Rank 慢，别的 Rank 也得等。  
ReduceScatter、AllGather 也是类似逻辑。

所以只要某些流因为闭环失效，持续把队列顶高，导致延迟拉长，  
它不需要把所有 GPU 都打坏。  
只要把一部分 Rank 拖慢，就足以让整个同步点变慢。

这也是为什么现场经常看到：

-   GPU 利用率不是全部掉到 0
    
-   平均带宽也不是完全不跑
    
-   但 Step Time 就是上去了
    
-   NCCL latency 就是有长尾
    
-   集群里总有几个“慢 Rank”在拖后腿
    

  

这类问题最容易误判成：

-   是不是模型变了？
    
-   是不是数据加载慢了？
    
-   是不是存储卡了？
    
-   是不是 GPU 有问题？
    

这些当然也都要查。

但如果你同时看到了：

-   ECN counter 上升；
    
-   CNP 很少；
    
-   发送速率不收敛；
    
-   NCCL latency 拉长；
    

  

那就要优先考虑：

**RoCE 的拥塞反馈闭环是不是断了**

  

> 在同步训练里，闭环失效造成的不是“局部不好看”，而是“少数慢流量把整个 Collective 拖长”。

  

![[Inbox/笔记同步助手/微信公众号/2026/09/images/6d8ddced1506ff39003025014be5f454_MD5.jpg]]

<u>07</u>

现场怎么验证

这种故障，最怕“看到一个 counter 就下结论”。

正确姿势一定是看时间线。

至少把下面几层串起来：

**第一层，训练框架层**  
看 Step Time 是从什么时候开始抖。  
看是不是与某个训练阶段、某个通信阶段、某个 checkpoint 窗口同步。

**第二层，NCCL 层**  
看 collective latency 有没有在同一时间窗口拉长。  
看慢 Rank 是否集中在少数节点或少数 rail。

**第三层，网卡层**  
看发送速率是否真的收敛。  
看接收侧是否真的有 CNP 回送。  
看不同节点之间参数和版本是否一致。

**第四层，交换机层**  
看 ECN counter 是哪个端口、哪个队列、哪个时间窗口在涨。  
看是否伴随 PFC、队列水位、buffer 异常。

  

> 排障的关键不是“谁的 counter 高”，而是“谁先变、谁没跟上、闭环断在了哪一段”。

  

![[Inbox/笔记同步助手/微信公众号/2026/09/images/b22a4046fb3633bb7be3e3547bdd4180_MD5.jpg]]

<u>08</u>

这类问题最容易被哪几种误判带偏

  

### 误判 1：ECN 上升，说明 DCQCN 没问题

不对。

ECN 上升只能说明交换机在打标。  
后面的 CNP、发送端降速、队列回落，才决定闭环是否完整。

### 误判 2：CNP 少，就一定是交换机没打到包

不一定。

也可能是你看的主机不是对应接收端。  
也可能是看的不是对应流量。  
也可能是不同主机之间统计口径不同。  
也可能是配置没有统一。

### 误判 3：PFC 不多，所以问题不严重

也不对。

很多时候，真正把训练拉慢的，并不是大规模 Pause。  
而是 DCQCN 没有及时把发送速率压下来，导致延迟持续偏高，先把 Collective 拖慢。  
PFC 只是更后面的保护机制。

### 误判 4：NCCL 慢，就是 GPU 问题

也不完整。

NCCL 慢，有可能是 GPU、PCIe、NUMA、网卡、交换机、拥塞反馈链条中的任何一段。  
不能只盯一边。

### 误判 5：这是 IB 问题模型

不是。

这篇讲的是 RoCE / DCQCN 闭环。  
Native InfiniBand 不是靠 ECN、CNP、DCQCN 这套机制工作的。  
IB 该看的是另一套问题模型，比如 Credit、XmitWait、SL/VL、Fabric 路径等。

> 最容易拖慢排障的，不是故障复杂，而是把错误的问题模型套到错误的现场上。

  

![[Inbox/笔记同步助手/微信公众号/2026/09/images/f0837ef6471ea23756f1cb516f0f6e3f_MD5.jpg]]

<u>09</u>

怎么修复

这种故障最忌讳的就是看到 ECN 上升，就急着去“改大阈值”。

这往往治标不治本。

因为这次问题的核心，不是交换机太敏感。  
而是闭环后半段没接住。

真正的修复思路应该是分层做：

**第一，先统一端侧版本和参数**  
驱动、固件、OFED、RoCE/DCQCN 相关参数，要确保一致。  
别让部分节点和其他节点跑成“两套世界”。

**第二，核对接收侧和发送侧的反馈链条**  
接收侧是否真的在按预期回送 CNP。  
发送侧是否真的在按预期收敛速率。

**第三，核对优先级与队列映射**  
lossless 队列、PFC、ECN、DSCP / PCP / TC 映射是否一致。  
否则你以为在看训练流量，实际上可能混进了别的流量。

**第四，核对业务流量模型**  
是不是 Incast 太强。  
是不是 checkpoint 或存储流量和训练流量共路。  
是不是多任务叠加把某些 leaf 端口打成热点。

**第五，再考虑 ECN 阈值是否合理**  
阈值当然重要。  
但它不是所有问题的第一根因。

这次案例最终恢复稳定，不是靠“单调阈值”解决的。  
而是通过统一端侧配置与版本、恢复反馈链条、重新校验队列映射后，  
让 CNP 能按预期回来，发送端能按预期收敛，  
队列高水位才真正被压下去。

  

> 真正的修复，不是让交换机“少报警”，而是让发送端在该降速的时候真的降下来。

  

![[Inbox/笔记同步助手/微信公众号/2026/09/images/8cebb8dbc872843e052e6bb83e2fdfd5_MD5.jpg]]

<u>10</u>

工程启示是什么

以为 RoCE 调优的重点，是“把参数调到某个最佳值”。

但从大量现场看，更基础、也更关键的一件事其实是：

**确认闭环是不是存在。**

因为一个“理论上正确”的参数体系，  
如果在某些节点上没有真正生效，  
或者发送侧、接收侧、交换机三边没统一，  
那它在工程上就不叫“调优”，而叫“漂移”。

而漂移最可怕的地方在于：

平时它不一定炸。  
压测也不一定暴露。

但一旦训练规模上来、Incast 上来、Collective 同步压力上来，  
它就会把尾延迟放大成性能事故。

这也是为什么做 AI 网络，不要只盯“峰值带宽”。  
要盯“拥塞时系统怎么收敛”。

因为真正把训练拖慢的，很多时候不是“跑不满”。

而是“该收的时候收不住”。

  

> AI 训练网络的关键，不只是峰值能力，更是拥塞发生时，端到端闭环能不能把系统重新拉回稳定状态。

```
==============================
先确认是不是“真的在同一时间窗口”
==============================
Step Time 是什么时候开始抖的？
NCCL collective latency 是否在同一时间窗口拉长？
交换机 ECN counter 是否在同一时间窗口上升？
队列水位、PFC、buffer 指标是否也在这个时间窗口变化？

================================
确认 ECN 是打在“你以为的那类流量”上
================================
ECN 上升的是哪个端口、哪个队列、哪个 traffic class？
这个队列是否真的是承载 RoCE 训练流量的 lossless 队列？
DSCP / PCP / TC 映射是否一致？
是否有其他流量（存储、管理、备份等）混入同一队列？

========================
确认接收侧是否真的在回 CNP
========================
对应接收主机上，是否能看到 CNP 相关计数增长？
看的是不是对应的那台接收主机，而不是别的节点？
接收侧驱动、固件、OFED 版本是否与集群一致？
接收侧 RoCE / DCQCN 相关参数是否生效？
是否只有部分节点 CNP 明显偏少？如果是，问题很可能就在那一批。
计数器名称和路径因厂商、驱动、版本不同可能不同，但“看接收侧是否回 CNP”这个逻辑不变。

======================
确认发送侧是否真的在收敛
======================
发送端是否能看到 CNP 处理计数增长？
目标速率、实际发速是否在拥塞窗口下降？
某些发送端是否始终“满速冲”，没有收敛迹象？
如果没有，说明 DCQCN 可能并未真正生效。

=================================
确认集群有没有“版本漂移”或“参数漂移”
=================================
驱动版本是否统一？
固件版本是否统一？
OFED / RDMA Stack 是否统一？
RoCE 参数模板是否统一下发？
重启后参数是否真的保留并生效？
新上架节点是否沿用了同样的基线？

=============================
确认训练流量模型是不是在制造热点
=============================
是不是某个 Collective 阶段更明显？
是不是某几个 leaf 端口长期更热？
是不是 checkpoint、数据落盘、日志写入和训练流量共路？
是否存在明显 Incast？
是否多任务叠加在同一个 rail、同一个队列、同一组链路上？

===========================
别忘了排除“看错对象”这种低级坑
===========================
ECN counter 看的是不是正确端口？
CNP 看的是不是正确主机？
交换机和服务器时间是否对齐？
是否误把累计计数当成瞬时变化？
是否只看平均值，没有看峰值时段？
```
